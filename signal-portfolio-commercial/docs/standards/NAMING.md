# Naming Conventions

Evidenced from `alembic/versions/`, `tests/`, and the service/model ticket
references actually used in this codebase.

## Migration files

Format: `<alembic_revision_hash>_<snake_case_description>.py`, e.g.:

```
04c418cbb547_row_level_security_and_append_only_.py
9c2e5b8a1f47_add_integration_inbox_tables.py
f4b2c8e0a913_inbox_events_routing_outcome.py
7a3f9c1d2e4b_ledger_evidence_class_and_nullable_fee.py
```

- The hash prefix is Alembic's own autogenerated revision id (`alembic
  revision -m "..."`) -- never hand-edit it or reuse one.
- The description is a short, snake_case summary of the *schema change*,
  not the feature/ticket it serves (e.g. `add_price_versions_table`,
  `ledger_sleeve_id`, `inbox_events_parked_reason`) -- read the list of
  migration filenames and you get a changelog of the schema, not a list of
  tickets.
- One additive concern per migration: adding a table gets its own
  migration (`add_managed_programs_table`); adding a column to an
  already-shipped table gets its own, separately named migration
  (`ledger_follower_connection_id`, `ledger_originating_analyst_id`,
  `ledger_external_observation_id`) rather than a single migration that
  bundles several unrelated column additions.
- Unlike the sibling `signal-copier` service (which numbers its own
  migrations sequentially, e.g. `0014_...`/`0015_...`, and has had to
  renumber a colliding one -- see that repo's "Renumber writer_lease
  migration to 0015 (0014 taken by command_ledger)" commit), this
  service's migrations are never sequentially numbered by hand: the
  Alembic-generated hash prefix already avoids collisions between
  migrations developed in parallel, so there is nothing to renumber.

## Test files

Format: `tests/test_<module_or_feature>.py`, one file per service module or
cohesive feature area, matching the `app/services/<module>.py` it
exercises 1:1 in the common case:

```
app/services/source_coverage.py       <->  tests/test_source_coverage.py
app/services/evidence_manifest.py     <->  tests/test_evidence_manifest.py
app/services/token_revocation.py      <->  tests/test_token_revocation.py
```

Route-level/integration tests that exercise a module through the HTTP
layer instead of (or in addition to) calling the service function directly
get a distinct `_route` suffix so the two are never confused:

```
tests/test_source_coverage.py         (service-level: compute_source_coverage)
tests/test_source_coverage_route.py   (route-level: GET .../source-coverage)
tests/test_platform_performance.py
tests/test_platform_performance_route.py
tests/test_public_fit_simulation_route.py
```

Test *function* names are full sentences describing the behavior under
test, not `test_<method>_<case>` shorthand, e.g.:

```python
def test_no_tenant_scope_set_means_no_rows_visible_not_all_rows(...):
def test_max_drawdown_uses_the_true_running_peak_not_just_the_previous_point(...):
```

This matters here specifically because a test name doubles as the
regression's own description when it's later referenced from a commit
message or from `docs/testing/REGRESSIONS.md`.

## Ticket-style references (INT-XXX, AD-XXX, CU-XXX, S\<n\>, M-\<screen\>-\<step\>)

This codebase does **not** encode ticket ids in filenames. Ticket/screen
references appear only in **docstrings and commit messages**, tying the
code back to the acceptance case or screen spec that requires it:

- `INT-XXX` -- an id from `INTEGRATION_ACCEPTANCE_CASES.json` in the
  Signal Platform Integration Correction Pack, e.g. `INT-027` ("All
  permitted source outcomes reach research"), `INT-040` (storage-ceiling
  policy, in the sibling `signal-copier` repo), `INT-035` (anti-
  fabrication test coverage referenced by `source_coverage.py`).
- `AD-XXX` -- an admin/owner-facing screen id from `dashboard_spec/screens/`,
  e.g. `AD-18` ("Audit log and release evidence"), cited directly in
  `app/services/audit_log.py`'s docstring: "See
  dashboard_spec/screens/AD-18.md for the full screen contract this
  implements a bounded slice of."
- `CU-XXX` -- a customer-portal screen id, e.g. `CU-06` (performance/max
  drawdown/win rate), `CU-13` (account/revoke-tokens).
- `PU-XXX` -- a public-site screen id, e.g. `PU-03` (public fit simulator),
  `PU-06` (methodology/risk/legal documents).
- `S<n>` / `M-<screen>-<step>` -- a slice or milestone id from the internal
  build plan, e.g. `S12 step 5`, `M-CU-06-02`.

When writing a docstring or commit message for work tied to one of these,
name it explicitly and verbatim (`INT-027`, not "the routing outcome
ticket") so it stays grep-able across the codebase and commit history.
