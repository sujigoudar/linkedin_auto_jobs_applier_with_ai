# Migrations

Source of truth: `alembic/versions/*.py`, `alembic/env.py`, `alembic.ini`.

## Convention

- Plain Alembic, autogenerated revisions with hand-written `upgrade()`/`downgrade()`
  where the change is more than a table/column add (RLS, append-only triggers, role
  grants). Revision IDs are Alembic's own random hex ids — filenames are
  `<revision>_<slug>.py`, never hand-numbered.
- **Real, sequential `down_revision` chaining** — every migration after the initial
  schema names the exact prior revision it follows; there is exactly one linear
  chain from `f1cbfcc4819c` (initial schema, `down_revision=None`) to the current
  head, no branches.
- `alembic/env.py` imports **every** model module explicitly before building
  `target_metadata` — "mirrors `tests/conftest.py`'s own reasoning: importing only
  the modules a given script happens to touch would silently drop tables from an
  autogenerated diff."
- The database URL is never hardcoded in `alembic.ini`. `alembic/env.py` resolves it
  from `ALEMBIC_DATABASE_URL` (for pointing migrations at a specific, possibly
  disposable, database — e.g. CI) or else `app.config.COMMERCIAL_DATABASE_URL` — one
  place (`app/config.py`) owns "what database does this process talk to."
- A migration that installs RLS policies, append-only triggers, or role grants calls
  `op.get_bind()` — Alembic's own connection, **still inside the open transaction**
  the prior migration's table creation ran in — rather than opening a fresh
  engine/connection, which would run in a separate transaction and couldn't see
  those just-created, not-yet-committed tables.
- Any such migration also passes its **own frozen snapshot** of the table names it
  applies to, never `app.db`'s live, ever-growing constants
  (`_TENANT_SCOPED_TABLES`, `_APPEND_ONLY_TABLES`) — see ADR-0001 for the real
  failure (`UndefinedTable: relation "release_reviews" does not exist`) this
  convention exists to prevent on a fresh `alembic upgrade head` replay.
- RLS-enabling and append-only-enforcing migrations have **no working downgrade**:
  `downgrade()` deliberately raises `NotImplementedError` rather than silently
  weakening a live database's isolation or immutability guarantees (ADR-0001,
  ADR-0008). The `relay_role` migration's downgrade is a real, working one (drops
  the policy, revokes grants, drops the role) since removing an access grant is
  always safe to automate, unlike removing a protection.

## Running migrations

```bash
alembic upgrade head
```

against `app.config.COMMERCIAL_DATABASE_URL` (or `ALEMBIC_DATABASE_URL` if set).
See `docs/requirements/ACCEPTANCE.md` — "`alembic upgrade head` verified end-to-end
against a real disposable Postgres cluster" is part of this codebase's own done-bar,
not merely a suggestion; SQLite or a mocked engine cannot stand in for it, since RLS,
`FORCE ROW LEVEL SECURITY`, and the append-only triggers are all real Postgres-only
DDL with no SQLite equivalent.

## Adding a new migration that touches RLS/append-only/role grants

1. Never import or extend `app.db`'s live `_TENANT_SCOPED_TABLES`/
   `_APPEND_ONLY_TABLES` constants from inside a migration. Define your own frozen
   tuple in the migration module itself, scoped to exactly the tables real at that
   point in history.
2. Apply via `_apply_row_level_security(connection, your_tuple)` /
   `_apply_append_only(connection, your_tuple)` using `op.get_bind()`, not a fresh
   engine.
3. If the change would ever need to be undone, write a real `downgrade()` — but if
   it enables or strengthens RLS/append-only, follow the established convention and
   raise `NotImplementedError` instead of writing one that silently weakens a live
   database.
