# Addendum: post-Phase-12 work (same session)

After Phase 12's own validation report was written, the user gave an
explicit follow-on instruction: "Do absolutely everything possible
throughout the entire solution that do not require external accounts to
be set up yet and infrastructure to be acquired yet." This addendum
records what changed as a result -- read alongside
`docs/12_validation_report.md`, which is not rewritten in place so the
original Phase 12 snapshot stays intact.

## Requirements re-classified since the Phase 12 report

- **CP-002 "Every component grant must qualify"**: NOT_RUN -> **PASSED**.
  `app/models/portfolio_version.py` (PortfolioVersion, immutable/
  append-only, RLS-protected) and `app/services/portfolio_rights.py`
  (`check_portfolio_rights`) now exist: a portfolio version is only
  rights-eligible when EVERY member sleeve independently qualifies; one
  ungranted or revoked sleeve denies the whole version. 5 tests,
  load-bearing verified.
- **CP-028 "Version transition"**: NOT_RUN -> **PASSED** (structurally).
  `PortfolioVersion`/`PortfolioVersionSleeve` are append-only via the
  same trigger mechanism as `ledger_entries` -- "historical membership
  is never overwritten" is a database guarantee, not a convention.
- **CP-003 "Grant expiry at effect boundary"**: PARTIAL -> **PASSED**.
  `app/services/publication_admission.py`'s `admit_publication_intent`
  now calls `check_portfolio_rights` fresh, immediately before
  `enqueue_intent` -- a real effect boundary exists and rechecks rather
  than trusting an earlier result.
- **CP-051 "Entitlement expiration"**: PARTIAL -> **PASSED**. The same
  `admit_publication_intent` gates new-exposure actions (OPEN/ADD) on
  `entitlement.authorizes_new_entry`, while deliberately excluding
  risk-reducing actions (STOP_UPDATE etc.) from that gate -- matching
  `entitlement.py`'s own payment/safety separation.
- **CP-045 "Single publishing mode"**: NOT_RUN -> **PASSED**.
  `app/models/publisher_writer_claim.py` + `app/services/publisher_writer_claim.py`:
  a durable `(channel, external_strategy_id) -> writer_identity` claim,
  enforced by a real primary-key uniqueness constraint (the actual
  fence, not just an application-level check-then-act).
- **CP-009 "Hypothetical composite labeling"**: NOT_RUN -> **PASSED**.
  `app/services/history_origin.py`: a composite's label is the WEAKEST
  of its components' labels, never upgraded because most inputs came
  from a real feed. Refuses an empty component list rather than
  defaulting to the strongest label.
- **CP-071 "Business versus investment P&L"** and **CP-036 "Fees and
  subscription cost"**: NOT_RUN / PARTIAL -> **PASSED** for the formula
  itself. `app/services/business_economics.py` implements docs/08's
  exact unit-contribution and break-even formulas, with no dependency
  on `app/models/ledger.py` (subscription revenue is never blended with
  trading P&L). Full business-economics REPORTING (pulling real numbers
  from a populated ledger + subscription table) is still open --
  nothing calls this module from real data yet.
- **CP-087 "Readiness reporting"**: NOT_RUN -> **PARTIAL**. `GET
  /healthz` exists and is truthful (a real FastAPI route, tested via
  `TestClient`), but it reports only process liveness, not the fuller
  readiness/degraded-state reporting `signal-copier`'s own health
  endpoint models.
- **CP-065 "Verified payment event"**: still PASSED, now additionally
  exercised over real HTTP (`POST /api/v1/billing/webhook/stripe`, 4
  tests in `tests/test_api.py`) rather than only as a unit-tested
  function.

## New infrastructure (no new requirement ID, but real capability)

- **`app/main.py` + `app/api/`**: a real FastAPI app skeleton --
  `GET /healthz`, authenticated `GET /api/v1/me` (exercises the real
  JWT decode + tenant-scope stack end to end), and the Stripe webhook
  receiver. Deliberately no routes for anything needing a real external
  credential.
- **Real Alembic migrations** (`alembic/`, `alembic.ini`): two
  revisions -- autogenerated table creation, then a hand-written
  revision applying the exact same row-level-security/append-only setup
  tests use, reusing `app/db.py`'s own functions rather than duplicating
  SQL. Verified end-to-end against a real disposable Postgres cluster
  (`alembic upgrade head` from empty succeeds; `alembic downgrade -1` on
  the RLS revision correctly refuses). CI now runs this same
  verification on every push (`signal-portfolio-commercial-ci.yml`'s
  "Verify Alembic migrations apply cleanly" step). A real transaction-
  visibility bug was found and fixed while verifying this (see that
  migration's own docstring and the commit message for `9aee05a`).
