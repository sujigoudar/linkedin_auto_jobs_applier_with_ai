## 0. Findings that change how every row below should be read

1. **The WC-11 "120 race vectors" test proves nothing.** `SC/test_wc11_race_vectors.py` docstring says it runs vectors "through the REAL lifecycle manager/engine". It imports no engine or lifecycle code. It drives `tests/workflow_reference_model.py` only. Its only assertion is `assert result in ("PASS","REJECTED_IMPOSSIBLE_ORDERING","FAIL")`, which is always true (FAIL is in the set). The handler's event names (`submit_first`, `add_requested`, ...) do not match the vector event names (`dispatch_attempted`, `add_trigger_received`, ...), so most events are no-ops. The 120 vectors are not evidence for any race, ordering or chaos item.
2. **Placeholder tests carry scenario tags.** `SC/test_wc06_intents_and_outbox.py::test_crash_before_outbox_claim_is_new_submission_on_restart`, `::test_crash_after_outbox_claim_before_dispatch_skips_broker_call` and `::test_crash_after_dispatch_mark_before_response_blocks_new_exposure` have bodies of `pass`. The last one is tagged `@pytest.mark.scenario("OPS-001")`, and `docs/workflow-contract/requirements_traceability.json` lists OPS-001 as TESTED_SIMULATOR. That claim is unsupported. Also `pass`: `SC/test_scn_b.py::TestSIZ004WrongSideLongStop` (wrong-side stop) and `TestINSValidation`. `SC/test_scn_b.py::TestCAP003PortfolioBackingDoubleCount` has no assertion at all.
3. **Weak assertions.** `SC/test_scn_c.py::test_ord_006_duplicate_fill` ends with `assert position is not None` (its own comment says "Store may sum fills"). `test_ord_007` and `test_ord_008` never simulate fill-before-ack or cancel; they only enter a position. `SC/test_scn_b.py::test_paper_live_different_despite_same_display_name` only checks that two SQL INSERTs produce two rows. `SC/test_track73_features_capability_mutations.py::TestLatencyCalculationMutations` tests Python datetime subtraction, not app code. `SC/test_wc03_hierarchical_budgets.py::test_concurrent_same_opportunity_one_wins` inserts raw SQL into a hand-made table (it tests SQLite UNIQUE, not the app). None of these are cited as evidence below.
4. **The "9,108 cases all pass" claim, precisely.** The 4,608 admission and 4,500 sizing vectors are two finite grids (axes in 51.19/51.20). In the default pytest run they hit the pure functions `app.workflow.admission.evaluate_admission` (`SC/test_wc05_admission_and_selection.py::test_admission_vectors_all_4608_cases`) and `app.workflow.sizing.size_linear_long` (`SC/test_wc04_sizing.py::TestSizeLinearLong::test_sizing_oracle_vectors`). In the recorded evidence (`docs/workflow-contract/evidence/APPLICATION_RESULTS_admission.json`) only 1,920 of 4,608 admission cases were engine-driven. 2,688 are `scope: module_not_engine` (pure gate). All 4,500 sizing results are `scope: engine`. The vectors cover long-only equity sizing in integer cents with `lot_step=1`. They do not cover provider, broker, asset class, order type, account type or short sizing. The engine only ever derives `authorization` as authorized/unauthorized and hard-codes `interpretation="entry"` (`app/engine.py:781-782`), so authorization=unknown/disabled and interpretation=conditional_unmet/ambiguous/observation are enumerated only against the pure function or the adapter fixture.
